## The mechanism

`/proc/cpuinfo` is generated by the kernel from its model of the machine. There
is one machine, so there is one answer, and every process asking gets it.

Namespaces virtualise specific things: process ids, network interfaces, mount
points, hostnames, users. **There is no CPU namespace and no memory namespace.**
Limits are enforced by cgroups, which are a completely separate mechanism that
constrains *usage* without altering what any file *reports*.

So the container reads the host's values because nothing was ever built to
change them. This is not a bug being worked around — it is two subsystems that
answer different questions, and the confusion comes from expecting one to know
about the other.

| Interface | Reports | What you probably wanted |
|---|---|---|
| `/proc/cpuinfo`, `nproc` | the machine's CPUs | `/sys/fs/cgroup/cpu.max` |
| `/proc/meminfo` `MemTotal` | the machine's RAM | `/sys/fs/cgroup/memory.max` |
| `/proc/uptime` | the machine's uptime | your process's start time |
| `/proc/loadavg` | the machine's load | your cgroup's PSI pressure |
| `df` | the filesystem's size | the volume's actual quota |

Every row is a real incident category.

## Reading the number that is true

```bash
# CPU: quota and period, in microseconds. "max" means unlimited.
cat /sys/fs/cgroup/cpu.max
# 150000 100000   → 150ms of CPU per 100ms period → 1.5 cores

# Memory, in bytes. "max" means unlimited.
cat /sys/fs/cgroup/memory.max
# 536870912       → 512 MiB
```

The arithmetic for CPU is quota ÷ period. It is worth doing by hand once,
because `150000 100000` does not look like "1.5 cores" until you have.

:::warning
Under cgroup v1 the paths and filenames are different —
`cpu.cfs_quota_us`, `cpu.cfs_period_us`, `memory.limit_in_bytes` — and a script
that reads only v2 paths silently finds nothing and falls back to the host
value, which is the failure it was written to prevent. Handle both, or check
which one you are on: `/sys/fs/cgroup/cgroup.controllers` exists only on v2.
:::

## What "throttled" looks like

An over-threaded process under a quota does not run slowly in a way that shows
up as high CPU. It runs, gets stopped at the end of each period, and waits:

```bash
cat /sys/fs/cgroup/cpu.stat
# nr_throttled     31
# throttled_usec   44400023
```

Thirty-one throttled periods and 44 seconds of throttled time, accumulated in
six seconds of wall clock by sixteen threads under a 1.5-core quota.

The reason this is worth measuring rather than describing: **CPU utilisation
graphs look fine.** The process is using its 1.5 cores, which against a
16-core host is about 9%, and the dashboard shows a comfortable service while
every request waits. `nr_throttled` is the counter that tells the truth, and it
is not on most dashboards.

This connects directly to A02's cgroups topic. What is new here is *why the
process chose sixteen threads*, which is that it asked the wrong file.

## Who gets it right, and who does not

**Cgroup-aware** — reads the limit:

- JVM 8u191+ and 10+ with `UseContainerSupport`, on by default
- .NET Core 3.0+
- Go 1.25+ sets `GOMAXPROCS` from the cgroup limit; earlier versions do not
- Node's `os.availableParallelism()` respects affinity, not the cgroup quota

**Not cgroup-aware** — anything reading `nproc`, `os.cpu_count()`,
`runtime.NumCPU()` on older Go, `sysconf(_SC_NPROCESSORS_ONLN)`, or `MemTotal`.
That is a very large amount of code, including most thread-pool defaults, most
worker-count defaults, and most "auto" tuning in configuration files.

The practical rule: **`auto` in a container means "auto from the host's
numbers"** unless you have specifically checked otherwise. Setting the value
explicitly from the limit is one line and removes the whole class:

```bash
GOMAXPROCS=2
JAVA_OPTS="-XX:MaxRAMPercentage=75"
UVICORN_WORKERS=2
```

`MaxRAMPercentage` rather than `-Xmx` is the better form, because it is a
percentage of whatever the container actually gets and survives the limit
changing.

## The other borrowed numbers

**Uptime.** `/proc/uptime` is the host's — in the lab container it reads about
five days, which is when the VM booted. A process that logs "uptime" from it
reports something meaningless. Use its own start time from `/proc/self/stat`, or
just record when it started.

**Load average.** `/proc/loadavg` is the whole machine's, including every other
container on it. A load of 12 on a 16-core host tells you nothing about whether
*your* cgroup is starved. PSI — `/sys/fs/cgroup/cpu.pressure` — is the
per-cgroup answer and is the one to alert on.

**Disk.** `df` inside a container reports the underlying filesystem. A 20 GB
volume on a 500 GB disk shows 500 GB, and the application happily fills past its
quota until writes start failing.

## Detecting where you are, reliably

```bash
grep -o hypervisor /proc/cpuinfo | head -1   # virtualised?
lscpu | grep -i 'hypervisor vendor'          # which one
cat /sys/class/dmi/id/sys_vendor 2>/dev/null # what the firmware claims
uname -r                                     # whose kernel
[ -f /.dockerenv ] && echo containerised
cat /proc/1/cgroup                           # v2 shows 0::/ inside a container
```

`systemd-detect-virt` does most of this in one command where it exists, and it
is not in a minimal image — which is itself worth knowing, because the tool you
reach for is often the one that was left out.

The DMI files are the interesting case. On a VM they identify the platform
precisely — `Amazon EC2`, `m6i.xlarge`. Inside a container `/sys/class/dmi` does
not exist at all, because `/sys` is mounted with a restricted view. **Its absence
is itself a signal**: no DMI plus a hypervisor flag means you are in a container
inside a VM, which is the census the first lab performs.

## Nesting, which is the normal case

The four layers under the lab container are not unusual — they are what most
people are actually running on:

```text
container            → /.dockerenv, cgroup limits
  kernel (shared)    → uname -r, not booted by this process
    VM               → hypervisor flag, vendor Microsoft
      hardware       → Intel i7-10700
```

A pod in a managed Kubernetes cluster is a container, in a VM, on a hypervisor,
in a datacentre. Each layer takes a small overhead and adds a boundary, and each
one can be the reason something is slow. Knowing which layer you are asking
about is most of the skill.
